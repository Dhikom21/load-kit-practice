Your build — the intelligence layer

Course D0020E · the working contract for each build · the big picture is in PROJECT.html

You are handed a running kit. It drives real pods on a real machine and writes down everything that really happened. Your job is to add the four things an on-call engineer actually wants — and to show them in the UI:

  • a scaler — how many pods do I need, right now?
  • a forecaster — what will the metric look like over the next few minutes?
  • an early-warning detector — is something about to go wrong, before the alarm trips?
  • a cause-finder — when it did go wrong, who caused it?

The one rule that keeps this clear: the kit already records the ground truth in every run folder. You never guess whether your work is good — you measure it against metrics.csv, diary.jsonl and impact.json. Nobody's forecaster is "the victim" in advance: the diary decides.

The architecture — where your work plugs in

Blue is the frozen core (it only changes with the instructor's approval). Green is what your group builds. The whole run happens on one node; after it, everything you need for grading sits in the run folder.

First, how a plugin works here (the only pattern you need)

You have one finished example to learn from: loadkit/plugins/scalers/step.py — every line is explained. Every plugin of every kind follows the same five connections:

  1. Registry — loadkit/registry.py: the name is mapped to a file, and @register("…") puts your class on the list.
  2. Config — loadkit.yaml: the name appears in an enabled list (scalers:, forecasters:, ui_panels:…).
  3. Scenario — a scenario file names it (e.g. scaler: {name: step, …}).
  4. One call site — the core calls you in exactly one place. For scalers it is _control_loop() in loadkit/engine.py.
  5. A test with no cluster — tests/test_step_scaler.py proves it works on plain data. Every plugin must pass a test without a cluster — that is how this whole kit is built, and how your work is checked.

The mechanics (1–3 and 5) are copy-paste. Your real work is the algorithm inside, and it is judged by the diary, not by a secret. Read step.py and target_tracking.py and the pattern is yours.

You choose the model and write it from scratch. Pick the short scenarios to develop on (they are written for a 4-core machine); prove it on one full scenario at the end.

The data contract is already in loadkit/forecast.py. The forecaster gets a context: history (every load's metrics, 15 s steps), horizon (steps ahead), and planned_events — the known future (planned bursts, job due-times, user surges) that Timestral can use as future covariates. It returns {series: {p10, p50, p90}} — those percentiles are your forecast bands, so the forecaster and the UI panel are one feature seen from two ends. Timestral is probabilistic and multivariate, so it fits this contract natively; your job is to call it inside timestral.py::_model and make it beat the built-in reference forecaster. The model's quantile head is deterministic — same input, same band — so no seeding is needed.

Installing Timestral (once, on the laptop): pip install git+https://github.com/mistralai/timestral.git — it is not on PyPI; needs Python ≥ 3.10 and pulls in torch. The standard model mistralai/Timestral-209M (~837 MB) downloads from Hugging Face on first use, then runs fully offline. Smaller sizes (123M / 28M / 5M) exist for weak machines, but the class standard is 209M, so all groups' numbers stay comparable.

Show it: the forecast-bands panel (post-run, in the replay view)

The panel already exists and is enabled: ui/panels/forecast.js (listed in ui_panels: in loadkit.yaml), fed by /api/runs/<id>/forecast, which calls the enabled forecaster. Read ui/app.js (how a panel works) and forecast.js (how the band is drawn from the p10/p50/p90 the API returns).

  • It draws the real metric line, shades between your p10 and p90, and puts a dashed line at p50. Open a finished run, pick a load and a metric, and the band appears at the end of the run.
  • Make it better: more metrics, a detector-alerts layer on top, or the live view (a later step).
  • Minimum-viable: the band renders for one load in one finished run (it already does — the marks are for a better forecaster behind it).

How you'll be graded (plain words)

  • Mechanical (must be present): registered, switched on in loadkit.yaml, a passing test with no cluster, visible in the UI. This is the entry ticket, not where the marks are.
  • Algorithmic (the marks): forecast quality (does the band contain reality? is the peak right?), warning lead-time (early? how many false alarms?), cause-finder accuracy (right load?). Report your numbers against the run folder — a claim without the number is not done.
  • Always: develop on a short scenario, then prove the same thing on one full scenario.

Your first 30 minutes

  1. make ui and open a past run (or run one).
  2. Read loadkit/plugins/scalers/step.py top to bottom.
  3. python -m loadkit run sensor-storm-short --seed 7; open the run folder and read README.txt, metrics.csv and impact.json.
  4. Open the finished run in make ui and look at the Forecast panel — the built-in reference band is already there. Your job is to make Timestral beat it.
